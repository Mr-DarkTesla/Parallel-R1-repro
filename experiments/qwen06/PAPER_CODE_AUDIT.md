# Статья и опубликованный код: проверка перед RL

Проверено по [arXiv v2](https://arxiv.org/html/2509.07980v2), последней доступной arXiv-версии, и форку commit `f1c63891d7fe77335103eb2c17e542a2b086dafc`. Это воспроизведение доступной реализации с Qwen3-0.6B; совпадение с результатами 4B из статьи не установлено.

| Механизм | Что обнаружено в коде | Значение для эксперимента |
|---|---|---|
| Триггер форка | main генерирует до `<Parallel>`, затем две coroutine через `asyncio.gather` | Форк выбирается моделью, число ветвей задает код. Параллельность — batching/планирование на одной GPU, а не две GPU |
| Изоляция | каждый Path получает одинаковый общий prefix, без соседней ветви | Независимость ветвей на стадии генерации есть |
| Summary и merge | код вставляет Path/Parallel/Summary-теги, генерирует summary, затем продолжает main | Закрытие и часть структуры обеспечены runtime, не целиком выучены моделью |
| Structured training | actor строит custom 4D attention mask и использует multiverse position IDs при log-prob/update | Работает только без remove_padding; SDPA выбран явно |
| Structured inference | vLLM принимает только `TokensPrompt(prompt_token_ids=...)` | Summary и продолжения получают обычную causal attention/обычные позиции; это расхождение с полной структурной политикой. Sampling и recomputed log-prob относятся к разным условным политикам |
| Position IDs | оба пути сбрасываются к одной базовой позиции, продолжение сдвигается по максимальной длине пути | Это перекрывающиеся диапазоны, а не буквально disjoint indices из текста §3.5.1; не называть их непересекающимися |
| Вероятности вставленных тегов | `response_mask` в upstream оставляет 1 для всех токенов; код исключения manual positions закомментирован | В loss попадают runtime-вставленные управляющие токены. Сохранено для воспроизведения кода; правильный policy-gradient для действия модели требует отдельного эксперимента с mask=0 на вставках |
| S1 | `math_dapo.py`: accuracy +1/-1 | Соответствует accuracy-only |
| S2 | `(global_step-1)%10 < 8`: accuracy, иначе +1.2 за correct + valid parallel, +1 за correct sequential, -1 иначе | Расписание 8/2 соответствует идее статьи. Код дополнительно требует корректного формата: malformed parallel при correct получает -1 в bonus-window |
| Верификатор | по умолчанию regex `Final Answer: ...`, лишь хвост последних 300 символов | Просто `\\boxed{...}` без строки Final Answer может получить -1. Проверка prompt/output format обязательна |
| Данные | train 17917, validation 1916, справочный SFT 4090 | Отдельные файлы в форке не подтверждают все состав/числа исходных экспериментов |
| Batch | статья stage2 512; `rl_exp_s2.sh` 256 на 8 GPU | Наш профиль одной GPU 32 — вычислительная адаптация, не полное совпадение гиперпараметров |
| Предел длины | upstream vLLM использовал остаток model context, path limit обрезался после генерации; объединение путей могло превысить response budget | Добавлены реальные max_tokens на main/path/summary и логирование generated/retained lengths. Финальная сериализация может обрезать parallel block; это явно отмечается |
| Предел форков | upstream останавливается после max_iterations (включая после summary), а не гарантирует финальный ответ | Лимит 4 сохранен. Такой trace может не содержать ответа; фиксировать stop/truncation и reward. Менять эту семантику в отдельной абляции |
| Figure 3 | готового вычисления и графика в стартовом RL-скрипте нет | Добавлен расчет по каждому открывающему токену / длине ответа; рост не гарантируется размером 0.6B |

Локальные изменения исправляют setup/runtime и добавляют наблюдаемость: validation S2 переведен на accuracy; step передается ДО rollout; шесть токенов проверяются атомарно; удален невалидный dummy chat-template call; пустые генерации обработаны; max_tokens соблюдается до генерации; запросы main имеют отдельные IDs; forward probe измеряет реальный вызов модели, не оценивает его по длине. Версия с исходным семантическим mask=1 сохранена, чтобы отделить воспроизведение кода от разработки исправленного метода.

Трейсы помогут проверить два разных утверждения: увеличивается ли относительное положение Parallel и меняется ли содержание ветвей с exploration на verification. Первое измеряется численно; второе требует содержательного просмотра примеров. Положение блока само по себе не доказывает причинное объяснение статьи.

Источники кода: `verl/verl/parallel_thinking_generation_v3/parallel_thinking_loop_v3.py`, `agent_loop.py`, `verl/verl/workers/actor/dp_actor.py`, `verl/verl/workers/rollout/vllm_rollout/vllm_async_server.py`, `verl/verl/utils/reward_score/math_dapo_acc_parallel_interved.py`, `math_dapo.py`, `verl/training_scripts/rl_exp_s1.sh`, `rl_exp_s2.sh`.
