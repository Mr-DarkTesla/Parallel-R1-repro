## Что нельзя делать с Claude

Предыдущие пять попыток запросить планы для внутренних thinking-трейсов через VK AI Proxy получили `[reasoning_extraction]` и стоили `$0.1455544`. Не следует отправлять Claude чужие или модельные thinking-тексты с просьбой извлечь, переписать или разметить их скрытые рассуждения.

Безопасный путь: просить написать **новое явное решение по одному условию без gold** либо консультировать по рубрике качества. Для уже написанного открытого решения разметку лучше сделать вторым Sol-исполнителем через локальный `assemble_agent_plans.py`: он вставляет только план и теги, а затем проверяет, что исходные слова и числа сохранены.

### Один допустимый запрос совета Claude

Перед генерацией можно сделать **один** ограниченный вызов, сохранив prompt и `cost_usd`. Смысл запроса:

> Мы собираем открыто написанные математические решения по условиям без эталонов для SFT Qwen3-0.6B. Предложи строгую рубрику отбора примеров с двумя независимо вычисляемыми подзадачами и одной явной операцией объединения. Не анализируй, не извлекай и не восстанавливай чужие private reasoning traces. Нужны только критерии выбора задач, частые дефекты и короткий шаблон открытого решения.

Ограничения: один вызов, модель и максимальный ответ фиксируются в prompt, прекращение при отказе, последующие поколения не запускаются автоматически. Этот совет не является ни генератором данных, ни заменой независимого review.

## Быстрый маршрут к 180 новым строкам

Цель: **180 новых относительно выбранного следующего train** примеров, не просто 180 файлов из архива. В наборе: 120 MATH и 60 GSM8K. MATH: 40 целых, 45 дробей/десятичных, 35 выражений. ARC не включать в эту цель: для большинства коротких вопросов невозможно получить две необходимые независимые вычислительные ветви; ARC оставляется в replay и eval.

Сейчас есть конкретный первый буфер из [203 сохранённых Sol 6.1
траекторий](audit/teacher_trajectory_candidates.md): 127 MATH и
76 GSM8K, ноль пересечений с accepted78, все с прежним верным
answer-precheck и полным `<think>`. Первичный независимый скрининг
допустил 201/203; это **только структурная пригодность**, ещё не
готовый датасет. Часть этих следов имеет одну длинную секцию без
границ; автоматический перенос по абзацам пока дал лишь 66
предложений и три смысловые ошибки при отдельном аудите. Их нужно
исправить/отсеять. Если после окончательной проверки окажется меньше
180, недостающие условия выбрать из `data/pool.jsonl` и генерировать
Qwen3-4B на нашем pod, где постобученная модель уже находится.

### Этап 0. Реестр и утечки

1. Сформировать `candidates_with_gold.jsonl` для машинной проверки и `candidates_blind.jsonl` только с `id`, `source`, `question`, `answer_type`.
2. До раздачи авторам запустить `dataset_survey/scripts/leakcheck.py` против полного корпуса eval и полного MATH test.
3. Отклонить точные дубли, варианты MATH test и сомнительные совпадения после ручного чтения.
4. После всех фильтров повторить leakcheck на финальных 180; результат должен быть `0` по eval и MATH test.

Команда из существующего протокола, требующая актуального пути к интерпретатору и corpus:

```bash
/tmp/exp21-audit-venv/bin/python -B \
  /Users/v.charkin/Documents/ChatGPT/R1/outputs/instruct4b-2026-10-06/dataset_survey/scripts/leakcheck.py \
  --input CANDIDATES.jsonl \
  --corpus /Users/v.charkin/Documents/ChatGPT/R1/outputs/instruct4b-2026-10-06/dataset_survey/eval_corpus \
  --out OUT_PREFIX
```

### Этап 1. Открытые авторские решения

Раздать blind-условия нескольким независимым авторам Sol 6.1 либо заранее подтверждённому 4B/DeepSeek-исполнителю. Каждый видит только условие и тип ответа, никогда не видит gold.

Контракт ответа:

- `<think>` содержит общий setup, затем две отдельные части `Part 1` и `Part 2`, затем явное объединение;
- каждая часть вычисляет разную необходимую величину из вопроса и общего setup;
- вторая часть не ссылается на первую;
- до частей нет найденного итогового ответа;
- внешний `Final Answer:` обязателен, но не должен быть встроен в prompt evaluation;
- при неуверенности автор возвращает `NO_SOLUTION`, а не подгоняет ответ.

После генерации сравнить внешний ответ с gold через `checks.correct`/`math_verify`. Несовпадение отправляет строку в reject, а не в исправление под gold.

### Этап 2. Только план и теги

Для ответов с верным итогом независимый второй исполнитель получает уже открытый текст и ставит только:

```text
<Parallel><Goal>
<Outline>1: ...</Outline><Outline>2: ...</Outline>
</Goal>
<Path>1: ...</Path><Path>2: ...</Path>
<Conclusion>...</Conclusion></Parallel>
```

Он не заменяет слова, числа или формулы. Общий setup остаётся до блока, объединение остаётся после него. Если границу нельзя провести без изменения текста, результат `NO_BLOCK`.

Использовать существующий `scripts/exp21/assemble_agent_plans.py`: он проверяет `<think>`, исходный ответ, grammar, `Final Answer`, отсутствие ответа до блока, ссылки между путями, дословное восстановление исходника и длину 4096 токенов. Базовый локальный валидатор `checks.py` дополнительно отсеивает пути короче 80 символов, дисбаланс, почти дубли, answer-in-outline и verification-only Conclusion.

### Этап 3. Две независимые проверки качества

Автоматика для всех кандидатов:

- корректность внешнего ответа и чисел;
- полная грамматика, нумерация и размещение целого блока внутри `<think>`;
- ровно две содержательные ветви, без ссылок между ними;
- текст автора восстанавливается после удаления тега и служебного плана;
- prompt + response не длиннее 4096 токенов;
- два запуска leakcheck, как в этапе 0.

Затем:

1. прочитать не менее 20 новых примеров полностью;
2. независимый слепой reviewer читает 30 других строк вместе с вопросом и gold;
3. gate: минимум 27/30 полезных блоков и 30/30 внешних и промежуточных вычислений верны;
4. один неверный итог, зависимая Path или раннее вычисление ответа исключает строку; если ошибка повторяется по типу, остановить соответствующую подгруппу.

В финальный train идут ровно 180, все reject и причины сохраняются в audit. Новые положительные строки смешиваются с прежним thinking/no-thinking replay одинаково в tagged и plain control. Plain control получается детерминированным удалением только структурных тегов и plan-scaffolding, с равенством базового математического текста и одинаковым порядком ID.

## Риски и решения до запуска

| Риск | Предохранитель |
|---|---|
| «180» получаются архивными дублями | ID manifest сравняется со всеми фактическими train/replay/eval файлами до авторства |
| Claude снова откажет в reasoning extraction | Claude используется только для одного запроса о рубрике; в траекторный путь не входит |
| 4B/DeepSeek недоступен или не подтверждён | Не запускать его по предположению; начать с Sol 6.1, а новый model route фиксировать отдельной проверкой |
| Верен итог, но ветвь содержит ложную математику | Blind review проверяет весь текст, а не только `math_verify` |
| Две ветви являются перефразировкой или проверкой | Формальный `checks.py` плюс смысловое независимое review |
| Разметка повредит решение | Дословное восстановление текста и чисел после удаления структуры |
| Превышение бюджета | Сначала reuse и CPU-гейты; платные авторы только после сверки ledger, не выше пользовательского лимита $200 |

Сначала разметить и проверить 203 сохранённые Sol-траектории, не
превращая первичный скрининг в автоматическое принятие. Чтобы
добрать до 180 полезных новых блоков, разрешённый следующий источник
Qwen3-4B уже доступен на нашем pod. DeepSeek-маршрут пока не
подтверждён. Claude Opus уже дал отдельный
[совет по методике](audit/claude_advice_response.md); новый платный
вызов ради общей рубрики не нужен.
