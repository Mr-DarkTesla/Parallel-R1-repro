# Ревью: train/inference согласованность Multiverse-маски

## 1. Итог по коду

**Явного off-by-one бага в штатном случае нет.** Штатный случай: блок плоский (без вложенных блоков), и `path_count` вернул ровно столько Path, сколько модель реально сгенерирует. Я сверил оба файла построчно.

|---|---|---|---|

### A. Неверное число путей (самое важное)

**Модель сгенерировала меньше путей, чем ожидалось** (`expected_paths > actual`). После последнего реального `</Path>` состояние остаётся в фазе `gap`. Последствия:
- Conclusion, `</Parallel>` и весь последующий текст, включая ответ, получают позиции от `base` и не видят ни одного пути блока. При обучении они видели бы все пути с позиции `max(ends)`.
- Выход из `gap` возможен только через `<Path>`. Поэтому следующий `<Parallel>` не начинает новый блок: проверка на стр. 35 требует `phase == "plain"`.
- Это бьёт одновременно по accuracy (ответ не видит рассуждений) и по валидности последующих блоков.

**Модель сгенерировала больше путей** (`expected < actual`). После закрытия блока лишний `\n<Path>` попадает в фазу `plain`, и вызывается `path_count`. `rfind("<Goal>")` находит старый Goal, `fullmatch(r"<Goal>(.*?)</Goal>\s*")` не проходит из-за путей после Goal, и функция возвращает `0 or 1`. Получается блок из одного пути, который видит предыдущие пути. При обучении такой путь был бы sibling.

**Фолбэк `or 1`** срабатывает, если Goal не распарсился, число Outline не входит в {2,3,4}, нумерация не `1..n` или между `</Goal>` и `<Path>` есть текст кроме пробелов. В обучении блоки из одного пути запрещены (`StructureError`, стр. 71–72). При инференсе они разрешены молча, без логирования. Цепочка таких блоков фактически превращается в последовательный режим.

### B. Утечка структурного решения через маску при обучении

Это факт кода с гипотезой о последствиях. Строки 64–69: принадлежность токенов после `</Path>` определяется **заглядыванием вперёд**.
- Если дальше идёт `<Path>`, токен `\n` становится gap: позиция `base`, предыдущие пути скрыты.
- Иначе это Conclusion: позиция `max(ends)`, все пути видны.

Значит, на позиции `\n`, которая предсказывает `<Path>` или `<Conclusion>`, ответ закодирован в маске и позиции входа. Модель учится «не вижу siblings → `<Path>`», а не считать пути по Outline.

Следствия, которые нужно проверить:
- **Masked decoder.** Число путей фактически задаёт `path_count`, а модель подчиняется маске. Поэтому ошибка `path_count` превращается в структурную ошибку, а не корректируется моделью.
- **vLLM sequential (без маски).** Каждый `\n` после `</Path>` видит все предыдущие пути. Это ровно тот паттерн, который при обучении означал Conclusion. Гипотеза: это даёт смещение к преждевременному `<Conclusion>` или к рассогласованию числа путей с Outline. Кроме того, пути 2+ сами по себе вне распределения обучения, потому что видят чужие пути.

### C. Вложенность

При обучении вложенные `<Parallel>` внутри Path поддерживаются. `MaskedDecodeState` в фазе `path` их не распознаёт: внутренний `</Path>` закроет внешний путь. Это допустимо, только если в данных нет вложенности. Это нужно проверить счётчиком на CPU.

### D. Параметры сэмплирования

Факт: `torch.multinomial(softmax(logits))` — это T=1 без top-p/top-k. Если vLLM-бейзлайн использует другие параметры (например, T=0.6, top-p=0.95), сравнение masked и sequential смешивает эффект маски с эффектом сэмплирования. Конфиг vLLM я не видел.

### E. Гипотезы без подтверждения в коде

1. **Учитывается ли маска вообще.** То, что 4D-маска реально применяется бэкендом `sdpa` в вашей версии transformers и с вашими патчами verl, из показанного кода не следует. Если маска молча игнорируется, при обучении была обычная causal-маска с перемешанными position_ids. Ниже есть негативный контроль для этого.
2. **Строки паддинга.** Строки паддинга полностью `-inf` (стр. 449–450). При `micro_batch > 1` после `crop_padding` возможны NaN в логитах этих строк, а `NaN * 0 = NaN` в loss. Раз обучение идёт, вероятно `micro_batch = 1` или ядро даёт 0, но это стоит подтвердить.
3. **Совпадение `path_count` с валидатором.** То, что `path_count` даёт на gold-префиксах то же число, что ваш валидатор, не проверено. Регэксп `<Outline>\s*(\d+)\s*:` строже либо иначе устроен, чем формат валидатора.

## 2. Минимальный воспроизводимый тест

### Шаг 0 (CPU, все 1077/1077/1062 блока, плюс val): структурная эквивалентность

Это самый дешёвый и самый строгий тест: точное равенство без численного шума.

```python
from verl.utils.dataset.multiverse_structure import multiverse_structure, dense_mask
from masked_decode_state import MaskedDecodeState, path_count

def check_structure(resp_ids, tok, tags, path_open, path_close, eos_id):
    pos, groups = multiverse_structure(resp_ids, tags)
    m = dense_mask(len(resp_ids), groups)
    st = MaskedDecodeState(path_open, path_close)
    body = resp_ids[:-1] if resp_ids[-1] == eos_id else resp_ids
    for i, t in enumerate(body):
        if t == path_open and st.phase == "plain":
            n = path_count(tok.decode(resp_ids[:i], skip_special_tokens=False))
            assert n >= 2, f"path_count fallback at {i}"          # фолбэк не допускается
            st.expected_paths = n
        p, vis = st.append(t)
        assert p == pos[i], (i, p, pos[i])
        assert vis == m[i, :i + 1].tolist(), i
    assert st.phase == "plain"
    return max((len(g) for g in groups), default=0)
```

Дополнительно посчитать:
- число вложенных блоков: `groups`, где span лежит внутри span другой группы;
- распределение текста между `</Goal>` и первым `<Path>`.

### Шаг 1 (GPU, 1 val-сэмпл): full forward vs stepwise cached, per-token logprob

**Выбор сэмпла.** Gold val, не меньше двух блоков, хотя бы один блок с 3–4 путями разной длины (чтобы `max(ends)` играл роль), длина до 4096.

**Изменения кода, которые нужны:**
1. В `generate` вынести шаг декодера в функцию `decode_step(model, past, token, state, prompt_len, step)`. Её используют и `generate`, и тест, чтобы тест проверял именно этот код.
2. `rowmask` создавать с `dtype=model.dtype` и `torch.finfo(model.dtype).min`, а не с захардкоженным bf16. Иначе тест в fp32 невозможен.
3. Проверить, что `tok.encode(prompt)` в генераторе совпадает побайтно с `prompt_ids` из `__getitem__` датасета.
4. В тест брать `input_ids`, `bool_attention_mask` и `position_ids` прямо из `dataset[idx]`, а не пересчитывать их.

```python
def full_logprobs(model, ids, pos, bmask, P, T):
    ids, pos, bm = ids[:T], pos[:T], bmask[0, :T, :T]
    add = torch.zeros(T, T, dtype=model.dtype, device=ids.device).masked_fill(~bm, torch.finfo(model.dtype).min)
    out = model(input_ids=ids[None], attention_mask=add[None, None], position_ids=pos[None], use_cache=False)
    lp = out.logits[0].float().log_softmax(-1)
    return lp[P - 1:T - 1].gather(-1, ids[P:T, None])[:, 0]

@torch.inference_mode()
def stepwise_logprobs(model, tok, prompt_ids, resp_ids, path_open, path_close):
    state = MaskedDecodeState(path_open, path_close)
    out = model(input_ids=torch.tensor([prompt_ids], device="cuda"), use_cache=True)
    past, logits = out.past_key_values, out.logits[0, -1].float()
    lps = []
    for step, t in enumerate(resp_ids):
        lps.append(logits.log_softmax(-1)[t])
        if t == tok.eos_token_id:
            break
        if t == path_open and state.phase == "plain":
            n = path_count(tok.decode(resp_ids[:step], skip_special_tokens=False)); assert n >= 2
            state.expected_paths = n
        logits, past = decode_step(model, past, t, state, len(prompt_ids), step)
    return torch.stack(lps)
```

**Прогоны.** Цель — отделить реальный баг от численного шума.

| # | Сравнение | Ожидание |
|---|---|---|
| a | fp32, `sdpa`: full masked vs stepwise | max \|Δ\| ≤ 2e-3 нат по всем токенам ответа. Это решающий прогон. |
| b | fp32, `eager`: то же | то же. Если (a) и (b) расходятся, проблема в бэкенде и обработке 4D-маски. |
| c | bf16: full **causal** vs stepwise **causal** (`visible` всё True, позиции `arange`) | это оценка шумового порога bf16, а не допуск |
| d | bf16: full masked vs stepwise masked | p99 и max \|Δ\| по регионам не больше примерно 2× порога из (c) |
| e | Негативный контроль: full masked vs full causal | на путях 2+, gap и Conclusion \|Δ\| должен быть **много больше** допуска. Если нет, маска игнорируется, в том числе при обучении. |
| f | Формат обучения: маска в fp32 с `-inf`, форма `(B,1,T,T)`, под `autocast(bf16)`, как в trainer | совпадает с (d) в пределах порога (c) |

**Отчёт по регионам:** Goal, path 1, paths 2+, gap-токены, Conclusion, текст после блока. Структурный баг обычно концентрируется в одном регионе (gap, начало Conclusion или первый токен пути), а не размазан. Поэтому средний Δ по всей последовательности недостаточен.

**Диагностика утечки B (на том же forward).** На каждом gap-`\n` и на `\n` перед `<Conclusion>` сравнить `P(<Path>)` и `P(<Conclusion>)` при структурной маске и при causal-маске. Если при causal-маске `P(<Conclusion>)` на межпутевом `\n` высокая, гипотеза о причине поломок в vLLM sequential подтверждается. Прогон на 20–50 val-сэмплах даёт уже частоту, а не единичный случай.

## 3. Ранжирование двух GPU-экспериментов после текущих пилотов

Предусловие: шаги 0 и 1 пройдены, и в декодер добавлено логирование событий: фолбэк `path_count`, выход в EOS из фазы `gap`, `</Parallel>` или `<Parallel>` в фазе `path`/`gap`, расхождение числа путей с числом Outline. Если шаг 1 падает, сначала нужен фикс, и ранжирование ниже не актуально.

### №1. Матрица декодирования на готовых чекпойнтах (только инференс, без обучения)

Матрица: {M1, M2 pilot, untagged M2 control} × {vLLM sequential, masked decoder}. Для control только sequential. Параметры сэмплирования (T, top-p, max_tokens), сиды и набор val-задач идентичны. Несколько сэмплов на задачу, сравнение парное по задаче.

**Метрики:**
- accuracy;
- доля валидных блоков;
- **совместная метрика:** ответ верный и все блоки валидны;
- для masked — частоты логированных событий.

**Правило решения:**
- tagged-модели при masked decode заметно лучше по валидности, чем при sequential → дефицит в рассогласовании декодирования (утечка B и пути вне распределения), а не в обучении;
- обе плохи → проблема в обучении;
- accuracy tagged при masked decode не хуже control при сохранённой валидности → основная гипотеза подтверждена дёшево.

Почему первым: дёшево, без переобучения, и отвечает на главный развилочный вопрос.

### №2 (условно, по итогам №1). Повтор 32-шагового M2-пилота с маской без утечки

Это перерендер маски, а не новые аннотации. Новое правило: токены после `</Path>` видимы всем последующим токенам и сами видят все предыдущие пути. Их позиция равна `base + max(длины путей до сих пор)`. Следующий `<Path>` возвращается к `base`.

Правило детерминировано без заглядывания вперёд. Решение `<Path>` или `<Conclusion>` модель принимает, видя уже написанные пути и Goal, то есть учится считать. Декодеру больше не нужен `path_count`, и он одинаково корректен для обоих режимов. Цена — один `\n` протекает между siblings. Данные, сиды, LR и `tag_lr_mult` те же, что в пилоте M2. Оценивать по той же матрице, что в №1.

Запускать, если в №1 доминируют рассогласование числа путей, преждевременный Conclusion при sequential или фолбэки и застревания в `gap` при masked.

**Альтернатива №2.** Если №1 показывает высокую валидность в обоих режимах, а дефицит только в accuracy относительно control, структурный фикс вторичен. Тогда второй эксперимент должен быть про объём и смесь обучения на имеющихся данных. Но и в этом случае сначала стоит дёшево проверить на CPU, что val-задачи не пересекаются с ~360 уникальными train-задачами, повторёнными ~3 раза.
