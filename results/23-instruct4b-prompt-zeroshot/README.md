# 23-instruct4b-prompt-zeroshot: откроет ли Qwen3-4B параллельные блоки по одному промпту (2026-10-15)

Вопрос: если в гибридную Qwen3-4B добавить шесть тегов как спецтокены (эмбеддинг каждого равен среднему эмбеддингов кусков его
текста) и подробно описать в промпте, как пользоваться блоками, начнёт ли модель их использовать без обучения.

Ответ: со спецтокенами нет. Та же исходная модель, для которой теги обычный текст, следует формату почти всегда.

- Модель с тегами-спецтокенами блоков не открывает (0% в rollout и при обычной генерации). Формату она при этом следует: пишет два
  пути и итог, но на месте каждого тега выдаёт `>`. Спецтокен не может выиграть у своих кусков. При связанных эмбеддингах логит тега
  равен среднему логитов его кусков и поэтому не больше лучшего из них. По teacher forcing вероятность тега в первой позиции ответа,
  где формат требует `<Parallel>`, равна 0.0000.
- Если умножить выходные строки тегов на 2 (входные остаются средним), теги становятся достижимыми: rollout реально ветвится,
  3305 блоков на GSM8K и 3504 на MATH, все по id `<Parallel>`. Но модель путает теги между собой и уходит в циклы вроде
  `<Summary><Summary>...`. Из-за этого 52% / 75% ответов не доходят до итоговой строки.
- Исходная Qwen3-4B без спецтокенов с тем же промптом пишет блок в 100% ответов, структура валидна в 99–99.8%. Пути действительно
  разные: например, разбор случаев модуля и возведение в квадрат. Точность GSM8K +4.8 п.п., на MATH разница в пределах шума.

## Что запускали

Dev-задачи из exp 13 (GSM8K dev 296 задач × 4, MATH dev 482 × 2), бюджет 16384, T = 1.0, top_p = 1.0, один под 4×H100 в очереди
`root.shared` (вне гарантии). Промпт: `scripts/exp23/header.txt`. От промпта авторов он отличается тем, что блок обязателен
(от одного до четырёх), шаги расписаны (когда открывать, пути не видят друг друга, пути должны различаться, что писать в Summary)
и есть шаблон блока. Модели:

- P: `Qwen3-4B-instruct-add-special-token` из exp 13, теги = среднее кусков, эмбеддинги связаны;
- P×2: P с развязанным lm_head, выходные строки шести тегов умножены на 2 (`scripts/exp23/scale_tag_logits.py`);
- C0: исходная Qwen3-4B, теги в промпте и ответе обычный текст.

Режимы: rollout авторов в шаблоне non-thinking (ветвление по id `<Parallel>`, два пути, до четырёх блоков) и обычная генерация
non-thinking и thinking с записью id сгенерированных токенов.

Перед запуском проверено (`checks/check_tokens.log`): каждый тег кодируется одним id 151669–151674, все 16 тегов в отрисованном
промпте одиночные id, строка эмбеддинга тега равна среднему строк его кусков. В обычную генерацию промпт подаётся готовыми id,
а не текстом. В каждой строке дампа vLLM получил ровно 16 id тегов.

Почему у P×2 так падает точность. Плохих рассуждений тут нет: среди ответов с итоговой строкой точность P×2 в rollout 94.3 (GSM8K)
и 82.0 (MATH) против 93.1 и 74.7 у P. Падение даёт доля ответов без итоговой строки. В 52% (GSM8K) и 75% (MATH) ответов тег
`<Parallel>` встречается больше 20 раз. Цикл начинается внутри пути в 71% случаев, в основном тексте в 21%, в Summary в 8%. Путь в
rollout заканчивается только на id `</Path>`, поэтому зациклившийся путь съедает весь бюджет. Вторая причина: после четвёртого блока
rollout авторов заканчивает ответ, и P×2, открывающая блоки на каждом шаге, до `Final Answer` не доходит.

У P с новым промптом на MATH −5 п.п. по той же причине, только слабее. Без тегов модель пишет оба пути текстом, ответ длиннее,
5.8% ответов обрезаны бюджетом, 6.2% без итоговой строки. Среди ответивших точность 75.7 против 76.3.

Спецтокен или куски. В обычной генерации P×2 все теги в ответах выданы как id, кусков ноль (`<Parallel>` 1.03 млн id, `<Summary>`
2.7 млн, почти всё в циклах). P не выдаёт ни id, ни кусков: на месте тегов стоит `>` (id 29 или 397 `>\n`), с него начинаются 100%
ответов. C0 пишет теги кусками, как обычный текст, потому что спецтокенов у неё нет.

## Thinking: где появляются блоки

Подвыборка: первая выборка у первых 150 задач каждого набора (`scripts/exp23/make_subset.py`), бюджет 16384. Сравнение с thinking
исходной модели с обычным промптом (c0-dev-think из exp 13) на тех же строках.

| модель, промпт | GSM8K | MATH | полный блок внутри `<think>` | полный блок после `</think>` |
|---|---|---|---|---|
| C0, обычный | 98.67 | 98.00 | | |
| P, новый | 98.67 (0.00 [−2.67, 2.67]) | 93.33 (−4.67 [−9.33, 0.00]) | 0 / 0 | 0 / 0 (`>` на месте тегов в 100% / 98.7%) |
| C0, новый | 96.67 (−2.00 [−5.33, 0.67]) | 94.67 (−3.33 [−8.00, 0.67]) | 22.0 / 43.3 | 100 / 98.7 |
| C0, «блоки внутри рассуждения» | 97.33 (−1.33 [−4.00, 1.33]) | 92.67 (−5.33 [−10.00, −1.33]) | 9.3 / 14.0 | 92.7 / 86.7 |
| P×2, новый | 47.33 | 43.33 | теги в 83 / 90 (циклы) | теги в 54 / 55 |

Полный блок: `<Parallel><Path>..</Path><Path>..</Path></Parallel><Summary>..</Summary>` (`scripts/exp23/think_where.py`,
`checks/think_where.jsonl`).

Внутри `<think>` модель решает задачу обычным текстом. Блоки внутри `<think>` у C0 есть, но это черновики оформления, а не ветвление
рассуждения: первый блок стоит в среднем на 86–89% длины `<think>`, то есть уже после решения, и модель вводит его словами
вроде «So the parallel block would be:». Потом она переносит такой блок в ответ. Пути в ответе пересказывают уже найденное решение.

Промпт «блоки внутри рассуждения» (`scripts/exp23/header_think.txt`) прямо требует писать блоки между `<think>` и `</think>`,
а после `</think>` давать короткое решение без тегов. Модель этого не делает: полных блоков внутри `<think>` стало меньше (9.3% / 14.0%
против 22.0% / 43.3%), они снова стоят в конце (медиана 86–87%), а блок в ответе остаётся в 93% / 87% ответов. Рассуждение
короче (4105 / 6494 символов против 7799 / 9106), о путях модель в нём почти не думает (слово path в 27% / 24% против 97% / 92%).
Указаниям о содержимом thinking Qwen3-4B без обучения не следует.

P×2 зацикливается уже внутри `<think>`: закрыт он только в 55% ответов. На полном GSM8K dev P с новым промптом в thinking даёт 97.64
против 96.71 у C0 (+0.93 [−0.76, 2.70]), блоков 0.5%.

## Выводы

1. Среднее эмбеддингов кусков при связанных эмбеддингах делает тег недостижимым на выходе, промптом это не исправить.
   Тот же дефект после SFT нашёл exp 20, там его лечил повышенный lr для строк тегов.
2. Простое масштабирование выходных строк делает тег достижимым, но шесть тегов почти неразличимы: строки — средние кусков с общими
   `<`, `</`, `>`, максимальный косинус 0.74. Модель путает теги и зацикливается.
3. Промпт сам по себе работает в ответе: с тегами-текстом исходная модель открывает блок почти всегда, пути разные, точность не хуже.
   Внутри thinking блоков нет ни с одним из двух промптов: модель решает задачу, а блок оформляет в конце или в ответе.
   Чтобы блоки появлялись именно в рассуждении, нужно обучение на трассах с блоками внутри `<think>`.
   Для настоящего параллельного вывода без обучения логично ветвиться по текстовому `<Parallel>` (стоп-строка) и вставлять
   структуру детерминированно, как в rollout с фиксированным числом путей для Qwen3-4B (`counted_loop.py`, rl4b-nosft).
