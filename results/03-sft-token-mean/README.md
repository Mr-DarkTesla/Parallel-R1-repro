# 03: нормировка loss по токенам всего батча

База: эксперимент 02 (ветка `exp/02-sft-prompt-positions`). Отличие одно, в `fsdp_parallel_sft_trainer.py`.

## Что исправлено

1. **Веса токенов.** У авторов loss — среднее по токенам внутри примера, потом среднее по примерам, так что токены длинных
   ответов весят меньше. Теперь loss — сумма по всем токенам ответов батча из 128 примеров, делённая на их число.
   С несколькими GPU число токенов складывается по всем GPU, поэтому результат не зависит ни от micro batch, ни от числа GPU.
2. **Масштаб градиента.** У авторов `training_step` делит loss микробатча на число микробатчей уже после `backward()`,
   который вызывается внутри `_compute_loss_and_backward`. Градиент получался суммой по микробатчам: в 16 раз больше
   среднего у авторов (micro batch 1, 8 GPU), в 32 раза — в 01 и 02 (micro batch 4, 1 GPU). Теперь нормировка стоит до `backward()`.

Добавлен лог `train/grad_norm` (норма до клиппинга).

## Выводы

- Измеримого эффекта нет. Точность и структура в пределах шума: MATH300 25.3 против 26.9 при 316 задачах — разница меньше
  двух стандартных ошибок; AIME и AMC по 30–40 задач ещё шумнее. Это один сид на вариант.
- Почему так: Adam почти не зависит от масштаба градиента, а клиппинг в 02 срабатывал на каждом шаге и сводил норму к 1.0.
  Ошибка масштаба в коде авторов на обновления почти не влияла. Остаётся только разница в весах токенов, и на этих данных
  (ответы 300–2500 токенов) она не видна.
- Исправление корректное и дешёвое, его можно оставить. Но вывод «нормировка улучшает SFT» эти данные не подтверждают.
  Чтобы различить варианты, нужны 2–3 сида.
